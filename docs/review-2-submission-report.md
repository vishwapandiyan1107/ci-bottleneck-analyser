# Review 2 Submission Report — CI Bottleneck Analyser

## Review 1 feedback addressed

This iteration directly implements the three improvement items from Review 1: (1) concrete empirical baseline values with a formulaic definition of median developer feedback time, (2) automated end-to-end tests for CI event ingestion and threshold triggers, and (3) a documented provider-neutral webhook/streaming simulation for GitHub Actions, GitLab CI and Jenkins.

## Architecture

The application is a full-stack TypeScript prototype. The React/Vite client provides Overview, Build Explorer, Bottleneck Analysis, Recommendation Review, Experiment, Audit Trail and Threshold Configuration screens. Express exposes the tRPC API under `/api/trpc` and a reviewer-facing calculated endpoint at `GET /api/analysis`. `server/analysisEngine.ts` owns CSV/JSON parsing, validation, deterministic rules, recommendations, optimisation measurement and FP/FN evaluation. `server/analysis.ts` is a stable compatibility entry point. `server/persistence.ts` stores review state, settings, recommendations, integration event IDs and audit events in a local JSON store when no database is configured; Drizzle schema definitions are included for deployment persistence.

## Empirical baseline and metric definition

The canonical validation dataset is `data/ci_build_logs.csv` with 648 reproducible synthetic records. For each valid build `i`:

`feedbackTime_i = durationSec_i`

`medianFeedbackTime = median(feedbackTime_1 ... feedbackTime_n)`

`durationSec` is the end-to-end queue-to-completion interval visible to the developer, so `queueSec` is a secondary metric and is not added again. With 648 records, sorted central durations are 701s and 702s, giving `(701 + 702) / 2 = 701.5s = 11.69 min`.

Empirical baseline: median feedback 11.69 min; P90 feedback 14.83 min; median queue 3.40 min; mean cache hit 63.02%; mean agent utilisation 75.77%.

The default deterministic optimisation scenario calculates: median feedback 11.69 → 9.87 min (15.62% lower); P90 14.83 → 13.18 min; median queue 3.40 → 2.67 min; mean cache hit 63.02 → 74.65%; mean agent utilisation 75.77 → 74.66%. These values are generated by the analysis engine, not manually entered dashboard claims.

## Deterministic analysis rules

The analyser validates duplicates, negative/inconsistent durations and malformed supplied timestamps before analysis. Rules detect: cache opportunities when dependency-install cache hit is below the configured threshold; queue bottlenecks from median queue share; slow tasks when task duration exceeds the configured task-median multiplier; agent saturation at or above the utilisation threshold; and parallelisation opportunities only when dependency information is known and sequential-to-parallel improvement exceeds the configured threshold.

Each detected signal contains label, severity, confidence, evidence and estimated impact. Recommendations contain proposed change, owner, risk and rollback instructions.

## End-to-end pipeline tests

`server/integration.e2e.test.ts` starts a real Express server and uses Node `fetch` to exercise the HTTP boundary. Tests verify GitHub Actions-style agent-log ingestion, queue and agent threshold triggers, configuration changes affecting later events, audit recording, calculated `GET /api/analysis`, malformed event rejection and duplicate `eventId` idempotency. Recommendation unit tests also verify approve → apply → rollback restores the previously reviewed state.

## Integration / streaming stub

The prototype exposes:

- `GET /api/analysis` — calculates analysis from the canonical reproducible dataset.
- `GET /api/integration/health` — reports the integration contract and supported providers.
- `POST /api/integration/ci-events` — accepts one canonical CI record or a small batch.

Supported provider identifiers are `github-actions`, `gitlab-ci`, `jenkins` and `generic`. Each POST represents a discrete webhook/stream event. Repeated calls simulate continued streaming; `eventId` is persisted so duplicate deliveries return HTTP 409 instead of being applied twice. A future provider adapter only needs to map native provider payloads into the canonical telemetry schema before sending the event to the same validation and analysis pipeline.

## Governance, audit and rollback

Recommendation decisions support approve, reject, override, apply and rollback. Every decision requires a human-readable reason. Apply stores the prior reviewed state; rollback restores that state and records a separate `Rolled back` audit event with evidence and configuration version context. Threshold updates are versioned and auditable. High-impact changes remain behind human review.

## Edge/failure cases

The dataset and validator cover duplicate records, negative/inconsistent durations, malformed timestamps when supplied, missing/unknown dependency evidence, insufficient parallelisation evidence and agent saturation. These cases are surfaced as validation or guarded analysis conditions rather than silently producing unsafe recommendations.

## Validation quality

The validation dataset carries expected labels for rule-consistency testing. The implementation compares each labelled record with its per-record primary rule prediction, avoiding the earlier global-label counting error. The resulting binary detection metrics are calculated by the engine and exposed in the Experiment dashboard as TP/FP/TN/FN, precision, recall and F1.

## Reproducibility and documentation

`pnpm run generate:dataset` recreates the canonical dataset. `pnpm run test`, `pnpm run test:e2e`, `pnpm run check` and `pnpm run build` are the project verification commands. Documentation is provided in `docs/requirements.md`, `docs/validation-report.md`, `docs/review-fixes.md`, `docs/integration.md` and `docs/limitations.md`. `data/validation-summary.json` stores machine-readable baseline and experiment evidence.

## Prototype boundary

This remains a field-ready prototype, not a live CI-control plane. The external provider mutation/authentication layer is intentionally a stub; the project demonstrates the ingress contract, analysis, governance, measurement and rollback state model without claiming live production changes or production savings.

## Review 2 hardening additions

The submission now exposes an explicit experiment evidence object: empirical baseline, 15% reduction target, <=10 minute guardrail, measured result, absolute target error, relative target error and target-met status. The dashboard renders the same calculated values.

The integration layer now includes a provider-native adapter endpoint at `POST /api/integration/webhooks/:provider`. Native-style GitHub Actions payloads are normalized into the canonical telemetry contract and then pass through the exact same validation, threshold, recommendation and audit pipeline. A replayable fixture and e2e test are included.

The verification package therefore directly covers the three review improvement areas: reproducible empirical measurement, automated HTTP end-to-end validation, and a concrete webhook/streaming simulation with an explicit production integration boundary.
